# Model Card for AM2 anomaly detection model

<!-- Provide a quick summary of what the model is/does. -->

The CLOSER project collects a large number of questions and variables from UK longitudinal population studies. We enable researchers to discover data of interest by using a web portal (discovery.closer.ac.uk)to browse questions and variables, or by querying a REST API (https://github.com/CLOSER-Cohorts/colectica-api) to get data programmatically from the repository our data is stored in. Our data is like a graph database: items are nodes, and can reference each other.


## Model Details

### Model Description

<!-- Provide a longer summary of what this model is. -->

You can represent the relationships that an item has with other items as a vector of numeric values. Below is an example of the relationships that a variable has with other items: (5=directly references, 1 = transitively/indirectly referenced i.e. Variable Set->Variable Statistic-> Variable, 0 = no relationship).

We can create a pseudo-labelled training dataset for a supervised learning model using PCA, IsolationForests and a ‘human in the loop’ . A human user uses a Python function called “train_semi_supervised_model” to create pseudo-labelled training data. When running this function, they will be presented with the graphs showing the output from the IsolationForest and the data for the outliers detected by the IsolationForest. The user will be asked to confirm if the outliers are anomalies that require human intervention. This could be ascertained by viewing the outlier in the Discovery web portal, examining what other items the outlier is/isn’t connected to, etc.
We will use this pseudo-labelled data to train a decision tree which will predict anomalies. 

We take the data representing item relationships, and perform dimension reduction by using PCA. We identify outliers in the pca data using a IsolationForest. A ‘human in the loop’ examines those outliers and confirms whether they are genuine anomalies OR if they’re just items that are unusual.

So we can go from a set of numeric vectors representing item relationships, to a PCA plot which shows outliers identified using an IsolationForest, which a human can inspect for anomalies.

When we have generated a pseudo-labelled dataset, a supervised model (e.g. decision tree) is trained on the pseudo-labelled data; the input features are the numbers representing relationships that an item has with other items (as described in previous slides). The target variable (e.g. the ‘IsAnomalyFlag’ value in the example below) are the labels generated by the ‘human in the loop’ by examining the IsolationForests: 0=fine, 1 =anomaly.

## Uses

<!-- Address questions around how the model is intended to be used, including the foreseeable users of the model and those affected by the model. -->

We want to find items which are ‘anomalies’; they’re either connected to another item they shouldn’t be, OR they’re not connected to an item that they should be.
Anomalies cause problems in the web front end (items aren’t displayed correctly, items can have missing information, or irrelevant/confusing information, etc.) 
Anomalies also cause problems when executing queries against the REST API we use to expose our data; if there isn’t a direct path from one item to another, certain queries won’t work. For example, a variable item that isn’t referenced by a dataset item won’t be returned in a query that requests all the variables in that dataset.

Hard-coding rules for all potential anomalies is too time-consuming and difficult. There are too many potential relationships between items/item types, it’s too time consuming to create and maintain this list of rules. It also requires ‘expert knowledge’ that CLOSER staff may not have; we may not know that a certain relationship between items is required or problematic. The DDI-XML datatypes and schemas used in our system may change over time, requiring us to continuously create new rules, or abandon old rules.
Also, it’s important to remember that an outlier is NOT the same as an anomaly – just because an item has an unusual relationship with another item type, doesn’t mean that’s a problem. In our context, unusual is not equal to anomalous. 
Could an ML model can be used to predict anomalous items from existing data?
